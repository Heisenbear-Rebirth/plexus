## 发现与修复

| 问题 | 修复后的行为 | 验证 |
| --- | --- | --- |
| Claude 初始化已有模型名时可能不读取思考强度；原生 `apply_flag_settings` 成功后仍保留旧值。 | 初始化和已确认的设置修改触发原生设置读取；核对完成前暂停维护与额度接续。响应中的基础模型名不能覆盖已确认的 `[1m]` 选择。 | 实际 wrapper + 协议子进程，修改 high 到默认值并确认重新可用；初始化、重启与查询期间新输入用例。 |
| Claude 只读请求超时后仍占据请求表，累计 32 次后所有查询永久被拒绝。 | 超时读取释放槽位，以每个 channel 独立命名空间识别并吞掉晚到回复；原生 interrupt 超时仍保持未知结果保护。 | 连续 40 次超时后查询成功，旧回复不能完成新请求或泄漏到 IDE；interrupt 晚到确认测试。 |
| Codex 明确选择默认思考强度的 `null` 与尚未读到设置的 `null` 混淆；缺失权限被哈希成一个假有效值。 | 明确默认值有已知标记，实际切换可被识别；缺失权限保持未知，停止控制直至同步。 | 原生 IPC 夹具拒绝未知权限下的发送和压缩；两端默认值变化的维护/额度恢复测试。 |
| 补交回执与维护恢复使用不同的模型/设置比较逻辑。 | 共用设置缺失和模型比较规则；基础模型名与已选窗口表示差异可兼容，真实变更、同步中状态仍拒绝旧回执。 | 同一回执依次经历设置未就绪、明确清空 effort、恢复原设置，只有最后一次接受且不重发提示。 |
| Codex 在限额失败后重新保存进度时，未把已核验的额度结果传给原生接续；暂停流程和按钮也未完整使用账户额度。 | 暂停维护继续查询额度；发送新交付前再次查询并向原生适配器传递结果，账户额度可启用合法接续入口。 | Codex 额度暂停交付只提交一次，且原生适配器收到新鲜额度结果；UI 操作可用性检查。 |
| Codex 固定把 primary 标成短期额度，实际可能是每周额度。 | 保留 `windowDurationMins` 并按真实时长显示；缺少时长时使用“主额度窗口”等中性名称。 | 本机 API 返回 primary=10080 分钟；解析、视图和浏览器检查每周及五小时窗口。 |
| Windows 原生进程的额度时间戳可能比管理进程快几毫秒，刚查到可用仍被视为来自未来。 | 只对刚收到的原生读取归一化不超过 250ms 的正向偏差，原时间戳另行保留；过期和明显未来的结果继续拒绝。 | 实际跨进程测试出现 6ms 偏差；边界测试保留旧结果、251ms 和远期结果的拒绝行为。 |
| 卡片缓存未纳入模型、设置同步状态及维护能力；后台已就绪而按钮仍禁用。 | 相关字段变化立即重绘维护状态；无需等待其他字段偶然变化。 | 浏览器在同一页面切换 selectionPending，核对等待提示消失和按钮启用。 |
| 额度已确认可用时，上方标题仍显示“维护等待额度恢复”。 | 已恢复额度与尚待维护接续分别表达；待重启确认时显示对应确认状态。 | 浏览器同时核对“额度已恢复，可继续维护”和可操作按钮。 |
