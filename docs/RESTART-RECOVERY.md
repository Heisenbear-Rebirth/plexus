# 退出、关机和重新连接

2026-10-08 起，按用户要求取消思考强度及权限的前后一致性限制，覆盖 Claude、Codex 和 OpenCode。维护、恢复回执与额度接续使用当前原生设置；这些字段的变化或缺失本身不再阻塞流程。原生审批请求、会话身份、模型/代理、回执、文档、额度、未知投递及新输入检查仍有效。OpenCode 接入层也不再因这些设置改变而使维护状态版本失效，并在发送前继承最新 variant。详情见 [设置限制移除说明](SETTINGS-UNLOCK-2026-10-08.md)。

管理服务、Codex、Claude Code（包括 VS Code 面板）和 OpenCode 可以按任意顺序启动。项目重启后，管理页先弹出待接续会话列表。用户确认后，系统等待原会话连接，核对实际额度、维护进度及发送结果，再接续能够确认的阶段。客户端尚未启动或原会话尚未加载时继续等待。

需要重新打开**同一个原会话**。仅启动应用、但原会话仍未加载时，系统继续等待，不会另建会话代替它。

## 重启后的接续确认

- 覆盖退出前的上下文维护、额度恢复和保留消息，三类客户端使用同一确认入口。尚未连接的原会话也会列出，可以先确认再打开客户端。
- 点击“确认接续所选会话”只确认选中的会话；“稍后处理”或 Esc 保留任务与消息并继续暂停。稍后可通过工具栏“待确认接续”重新打开列表。没有打开管理页或没有确认时保持暂停。
- 选择保存在项目数据库中，刷新页面和打开另一标签页不会放行。下次重启管理服务时重新确认；旧服务、旧事项版本和重复确认都不能授权当前事项。
- 客户端在管理服务关闭期间才耗尽额度，或退出前的原轮次在服务重连后才耗尽额度，也会在检测到时加入确认列表。正常新任务不会继承旧轮次的接续请求。
- 确认后仍需等待真实连接及可用额度；不会把旧的“已连接”快照当作客户端已启动，不会解除未知发送结果、未知压缩结果或缺失回执的保护。
- 此入口管理本项目保存的维护、额度恢复和消息队列。未被管理服务或原生接入记录的任意业务中断，仍需用户在原会话确认任务进度。

例如：Codex / Claude 额度不足 → 关闭项目和客户端 → 关机 → 数小时后启动项目 → 在弹窗确认 → 打开同一个原会话。若实际额度已恢复且原轮次和设置对应，会提交一次继续提示；若先启动客户端再启动项目，使用相同规则。

## 等待额度时退出

Codex 中已结束的历史子任务不会阻塞接续。系统区分历史记录与尚未结束或无法核实的子任务；真正未结束的任务仍等待核对。等待就绪时也会继续更新额度，界面不会沿用过期的耗尽说明。

- 等待记录和排队消息保存在项目内。重新连接后重新读取实际额度，重置时间过去本身不代表恢复。
- Codex 使用原生最新失败轮次核对。Claude 在原生限额结果到达时同步保存最小状态到 `.plexus/claude-wrapper/quota-state/`，不依赖管理服务当时在线；重开后读取对应会话的原生历史，核对最后输入及限额错误。
- 只有原会话、工作目录、失败轮次和模型等设置对应，且没有新输入、人工停止或待确认工作时，才绑定新客户端实例，并使用已保存的“额度恢复”提示词继续一次。
- 发送意图已保存、结果却无法确认时，保留队列并提示核对。重启不会重新发送同一次继续消息。
- 新业务输入、人工停止或模型变更会使旧自动继续请求失效。思考强度与权限沿用当前原生设置，其前后差异不单独阻塞接续。历史文件缺失、正在变化或缺少对应证据时，等待核对。

## 上下文维护时退出

Claude 的 `--resume UUID` 与 `--resume=UUID` 均会触发原会话状态核对。“已连接，正在核对会话设置”无需反复重连；读取失败会自动重试。旧面板仍运行修复前的接入程序时，需在当前回复结束后重启对应连接。模型选择与实际响应模型名分开比较，`[1m]` 历史表示差异不会误报换模型；真正切换模型或上下文窗口仍需核对，思考强度与权限的前后差异不参与一致性限制。

维护因额度暂停后仍每分钟查询额度。已确认压缩操作失败且没有压缩边界时，显示“重新保存进度并继续整理”；只有当前设置、空闲状态和可用额度都确认后才启用。它会保存最新进度到新文档，保留旧交付与回执，并在新恢复完成后释放 FIFO。结果未知或已有压缩边界时仍核对原结果。额度接口缺少必要窗口时显示具体缺项，不把未知当成可用；可以在原会话查看 `/usage`。

| 退出时的阶段 | 原会话重新连接后的处理 |
| --- | --- |
| 正在停止原业务轮次 | 核对原业务轮次的结束边界，再发送交付请求。 |
| 正在写交付文档，尚未收到回执 | 新实例的历史仍对应原维护请求时，重发当前交付阶段；原进程仍在执行时保留其回执入口。 |
| 已收到交付回执 | 保留文档和内容哈希，核对原控制轮次结束后才压缩。 |
| 压缩请求尚未发送 | 核对原轮次及交付回执后发送一次。 |
| 压缩请求已发送 | 有对应请求的完成证据就进入恢复；结果不明则保留锁和队列，提示核对。 |
| 正在恢复上下文 | 只补未完成的恢复阶段，使用原交付文档，不重复压缩。 |
| 已收到恢复回执 | 核对该轮次结束后释放队列；按原流程决定是否发送继续提示。 |

仅管理服务重启、客户端进程仍存活时，也会持续核对当前轮次。启动时暂时连接不上，不会永久卡在一次失败的启动检查中。已因人工操作、设置变化或确定失败暂停的流程保留原原因；重启不是新的重试授权。

维护过程中同时耗尽额度时，仍保留维护锁和当前阶段，需在额度恢复后核对阶段；普通额度继续提示不会绕过维护回执。

## OpenCode 的额度边界

OpenCode 的维护接续及消息队列支持上述确认流程。当前失败轮次有原生 APIError / HTTP 429 时，系统将其视为待核对的限流，暂停上下文压缩及协作投递。它没有已接入的统一额度查询，不能仅凭经过几小时自动重试；请在原会话处理额度或限流并继续，新轮次正常后再释放队列。旧错误、普通文本和原生正在重试的轮次不被误判为已确认的额度恢复。

错误结构核对依据：[OpenCode 原生错误转换实现](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/session/message-v2.ts)。

## 重开后已连接，但自动接续暂缓

Claude 的初始化握手可能成功而尚未输出完整 system/init。接入会从本次启动的权限参数以及原生只读 get_settings 取得当前设置，核对原失败记录后再接续；不会把空字段当作设置改变，也不会发送业务提示来索取这些信息。实际设置变更、新输入和未知发送结果继续受到原有保护。

页面明确显示是否已连接、缺少什么信息、当前额度是否刚查询过，以及是否需要操作。旧面板会提示“已连接，重开面板后可加载修复”；请在合适时机关闭并重新打开同一个会话，管理服务会继续检查。

Codex 的自动审批模式可能由桌面端报告为 `guardian_subagent`，恢复后由原生返回 `auto_review`。诊断元数据将两者归为同一选择；维护不再要求权限指纹与旧记录一致。当前客户端的实际权限、原生审批与跨会话接收规则仍然生效。已暂停流程结合当前轮次核对，已取消流程和已有后续输入的旧控制轮次不自动重放。

维护暂停期间仍定期刷新连接和设置状态，原生会话离线或重连会反映到管理页。取消维护会移除对应的接续确认事项；单独的队列确认和暂存消息继续保留。正在等待原生状态的旧重试或核对操作不能覆盖后来取消的流程。

## Claude 已连接，但协作消息尚未接收

跨会话消息提交到传输通道不等于已经交给模型。Claude 可以因跨会话接收策略或权限模式不匹配暂存消息，并在等待超时后丢弃。新版接入跟踪这些原生通知，显示具体原因；消息丢弃后清除对应等待标记，恢复会话实际状态。接收策略不会被自动修改，消息也不会自动重发。

旧 Claude 面板需要在工作结束后重开同一会话以加载通知处理，管理服务或 Codex 重启不能替代这一步。无法确认接收结果时保留等待；有明确原生丢弃证据时才能移除对应标记。

发送适配器会在投递时读取发送方的实际权限，并使用 Claude 原生 socket 封装声明已知类别。双方类别一致时可由原生策略正常接收；类别不一致、状态未知或显式接收限制仍由 Claude 决定。该发送修复由管理服务加载，已经加载通知处理的 Claude 面板无需再次重开。

## Codex 空闲与账户额度

原生会话 idle 只说明没有正在执行的轮次，不证明账户有可用额度。管理服务通过独立额度接口每分钟查询一次，各 Codex 会话共享结果；即使模型无法回复也不依赖聊天消息触发。界面区分账户额度与任务活动，查询失败显示待查询。

账户额度不足时暂停新维护和排队投递，容量恢复后重新核对。只有当前原生轮次明确因额度失败，且原有设置、确认和任务证据仍一致，才提交一次自动继续；普通空闲或已完成的会话不会因为账户恢复而被唤醒。查询要求 Plexus 管理服务和 Codex 原生连接保持可用。

## Claude 额度窗口数据缺失

Claude 的额度端点失败时可能仅返回旧响应头中仍有效的窗口。若五小时窗口缺失而周窗口仍存在，页面显示“额度查询不完整”，而不是断言额度仍耗尽。后台继续查询，只有收到完整有效数据才自动接续；可在原会话查看 `/usage` 检查原生读取是否正常。客户端离线时请重新打开同一会话。

取消已经过时的维护不会伪造完成回执。若取消时正在处理新的用户输入，会等当前回复结束再评估新维护，保留原有阈值与自动管理策略。

## 有新输入后如何继续维护

保存进度阶段暂停、且尚未发起压缩时，管理页提供“按当前进度继续维护”。它会保留旧交付和回执，重新保存最新进度后再整理上下文，队列全程保留。当前回复运行中按钮会禁用，回复结束后即可使用；若本次服务启动尚未确认接续，先完成页面中的重启接续确认。

已有压缩请求时先核对原结果。Claude 已确认该请求失败、且没有压缩边界或完成记录时，可使用“重新保存进度并继续整理”；结果未知或已有完成边界时仍按原结果接续。新流程保留与旧流程的关联、原文档和回执。
